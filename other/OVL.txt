Полная техническая спецификация формата архивов PRP / RPK (Triumph Studios Engine)

Документ составлен по результатам анализа в Ghidra, реверса алгоритмов движка и
верификации на бинарных данных игр Overlord / Overlord: Raising Hell / Overlord
II.

1. Общие сведения о движке и формате

  - Движок: Проприетарный движок Creator3D / Triumph Engine (разработка Triumph
    Studios). В бинарном коде используются префиксы TE (Triumph Engine), TGC
    (Triumph Game Classes), TRE (Triumph Render Engine).
  - Форматы файлов: Файлы с расширениями .prp, .rpk, .pvp, .psp, .spk и .omp
    имеют абсолютно одинаковую структуру контейнера (RPK — Resource Pack).
      - .prp — основные пакеты ресурсов (модели, текстуры, материалы, логика).
      - .pvp — голосовые и звуковые ресурсы.
      - .psp / .spk — системные пакеты интерфейса и общих данных.
      - .omp — пакеты карт (Overlord Map Package, отличаются только сигнатурой
        OMP\0 в заголовке).
  - Принцип хранения данных: Контейнер представляет собой не файловую систему
    (как ZIP), а сериализованное дерево объектов C++ (Binary AST / Object
    Graph). Ресурсы внутри разбиты на типизированные чанки с таблицами смещений.

2. Анализ исполняемого файла (Overlord.exe) и защита

2.1. DRM-защита

  - Исполняемый файл накрыт защитой (SteamStub Variant 2.1 в Steam-версии или
    SecuROM в дисковых изданиях). Секция .text на диске зашифрована.
  - Функция точки входа entry() представляет собой стартовый
    распаковщик/протектор с динамическим вызовом API через GetProcAddress.
  - Решение: Распаковка утилитой Steamless (Overlord.exe.unpacked.exe) либо
    снятие дампа процесса через x32dbg + Scylla с восстановлением IAT. После
    этого весь C++ код в Ghidra становится читаемым.

2.2. Архитектура загрузчика в памяти

  - TGCResourcePackLoader — высокоуровневый координатор и стейт-машина загрузки:
      - Состояния: [PACK] Idle (0), [PACK] ReleaseDevice (1), [PACK] Unload
        Packs (2), [PACK] Load Packs (3), [PACK] Register Packs (4), [PACK]
        Allocate Device (5), [PACK] Done (6).
  - Конвейер асинхронных задач (Thread Command Data — TCD):
    1.  TGCLoadResourcePackTCD — фоновое чтение файла с диска в память.
    2.  TGCDecompressResourcePackTCD — декомпрессия zlib-блоков через
        TEZipCompressor.
    3.  TGCRegisterResourcePackTCD — регистрация распарсенных объектов в
        глобальном реестре TEResourceManager.
  - Ключевые функции:
      - FUN_004be430 — функция чтения пака: проверяет минимальный размер (\ge 37
        байт / 0x25), считывает весь файл в RAM через FUN_00448a50, закрывает
        дескриптор и запускает разбор.
      - FUN_004be230 — проверка сигнатуры архива (OMP\0 или RPK\0).
      - FUN_00447dc0 — системная функция расчета контрольной суммы файла.

3. Побайтовая спецификация формата PRP / RPK

Любой валидный архив состоит из трех последовательных частей:

┌─────────────────────────────────────────────────────────────┐
│ 1. ЗАГОЛОВОК (Header) — ровно 176 байт (0xB0)               │
├─────────────────────────────────────────────────────────────┤
│ 2. ТЕЛО АРХИВА (Payload / Node Tree) — переменный размер     │
├─────────────────────────────────────────────────────────────┤
│ 3. ФУТЕР ЦЕЛОСТНОСТИ (Security Footer) — ровно 16 байт (0x10)│
└─────────────────────────────────────────────────────────────┘

Полный размер файла на диске = 176 + data_size + 16

3.1. Заголовок (Header) — 176 байт (0xB0)

Все числа хранятся в формате Little-Endian:

| Смещение | Размер   | Тип         | Описание            | Значение / Пример                                                                                                    |
| :------- | :------- | :---------- | :------------------ | :------------------------------------------------------------------------------------------------------------------- |
| `0x00`   | 4 байта  | `char[4]`   | **Magic Signature** | `52 50 4B 00` (`"RPK\0"`) или `4F 4D 50 00` (`"OMP\0"`)                                                              |
| `0x04`   | 2 байта  | `uint16`    | **Major Version**   | `0x0006` (версия 6)                                                                                                  |
| `0x06`   | 2 байта  | `uint16`    | **Minor Version**   | `0x0046` (версия 70 $\rightarrow$ `6.70`)                                                                            |
| `0x08`   | 4 байта  | `uint32`    | **File / Item ID**  | Идентификатор пакета в реестре (например, `137`, `311`)                                                              |
| `0x0C`   | 4 байта  | `uint32`    | **`data_size`**     | **КРИТИЧНО:** Точный размер тела архива (Payload) в байтах, **строго без учета 176 байт заголовка и 16 байт футера** |
| `0x10`   | 160 байт | `char[160]` | **Archive Name**    | Внутреннее имя архива в ASCII (дополнено байтами `0x00`)                                                             |

3.2. Тело архива и иерархия чанков (Node Tree / Reference Table)

Тело начинается со смещения 0xB0 (176) и представляет собой рекурсивное дерево:
каждый узел — это либо Контейнер (содержит оглавление и дочерние узлы), либо
Лист (Leaf) (содержит чистые бинарные данные).

Структура Контейнера (Reference Table):

1.  Префикс (опционально): Некоторые вложенные таблицы начинаются с магических 3
    байт: 01 01 00.
2.  Управляющий байт (control_byte):
      - Бит 0x80 (128) — флаг наличия расширенных записей (has_large_entries).
      - Биты 0x00..0x7F (младшие 7 бит) — количество 1-байтовых записей
        (small_count).
3.  Расширенный счетчик (если has_large_entries == true):
      - 4 байта (uint32) — количество 4-байтовых записей (large_count).
4.  Таблица смещений (TOC):
      - small_count пар по 2 байта: [uint8 id, uint8 rel_offset].
      - large_count пар по 8 байт: [uint32 id, uint32 rel_offset].
5.  Данные дочерних элементов:
      - Начинаются сразу за таблицей смещений:
        \text{data\_start} = \text{table\_end} = \text{pos} + 1 + (\text{if large: } 4) + (\text{small\_count} \times 2) + (\text{large\_count} \times 8)
      - Смещения rel_offset отсчитываются от точки data_start.
      - Записи в таблице упорядочены по rel_offset. Длина i-го дочернего блока:
        \text{length}_i = \text{rel\_offset}_{i+1} - \text{rel\_offset}_i
        (для последнего блока — до конца полезной нагрузки контейнера).

Правила строгой валидации контейнеров (защита от ложных срабатываний):

Чтобы сырые бинарные данные (DDS-текстуры, шрифты, аудио, матрицы) с первым
байтом ≥ 0x80 ошибочно не принимались за контейнеры:

1.  sorted_entries[0]["offset"] обязан быть равен 0.
2.  Все смещения обязаны находиться строго в пределах блока: offset <= len(data)
    - data_start.
3.  Смещения должны монотонно возрастать.
4.  Сумма длины таблицы и длин всех дочерних элементов должна до единого байта
    совпадать с размером блока.

3.3. Футер целостности (Security Footer) — ровно 16 байт (0x10)

Находится в самых последних 16 байтах файла:

| Смещение от конца | Размер  | Тип      | Значение      | Описание                                                           |
| :---------------- | :------ | :------- | :------------ | :----------------------------------------------------------------- |
| `-16 .. -13`      | 4 байта | `uint32` | `EF BE AD DE` | Константа **`0xDEADBEEF`**                                         |
| `-12 .. -9`       | 4 байта | `uint32` | `AF DE ED FE` | Константа **`0xFEEDDEAF`**                                         |
| `-8 .. -5`        | 4 байта | `uint32` | `CRC32`       | **Инвертированная контрольная сумма CRC-32** всего файла до футера |
| `-4 .. -1`        | 4 байта | `uint32` | `Hash2`       | Вторичный хэш / ID (обычно `0x7C809B8B` или `file_id`)             |

4. Алгоритм вычисления контрольной суммы (CRC-32)

  - Полином: Стандартный полином IEEE 802.3 — 0xEDB88320 (таблица по адресу
    0x00A5D368: 00 00 00 00, 96 30 07 77, 2C 61 0E EE, BA 51 09 99...).
  - Особенность Triumph Engine: В функции FUN_00447dc0 игра считает CRC32 по
    всему файлу от байта 0 до байта EOF - 16 и сохраняет его без финального XOR:
    \text{Engine\_CRC} = \sim\text{Standard\_CRC32}(\text{file\_data}[:-16]) \ \& \ \text{0xFFFFFFFF}
  - Реализация на Python:
    import zlib

    raw_crc = (~zlib.crc32(final_binary)) & 0xFFFFFFFF

* **Реализация на Rust (`crc32fast`):**
  ```rust

  hasher.update(&final_binary);
  let raw_crc = !hasher.finalize(); // бинарная инверсия NOT

5. Типы ресурсов движка (High-Level Assets)

Каждый высокоуровневый ресурс идентифицируется 4-байтовым заголовком типа
(TypeIdentifier / Сигнатура):

| Сигнатура (HEX)                        | Класс в движке                      | Описание и внутренняя структура                                                                                                                                          |
| :------------------------------------- | :---------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`3D 00 41 00`**                      | `TRETextureResource` / `DDSTexture` | **DDS Текстура:** Заголовок (`width: u32`, `height: u32`, `format: u32` \[7=DXT1, 9=DXT3, 11=DXT5, 5=RGBA\]), цепочка мипмапов с маркерами `24 00 41 00`.                |
| **`99 00 41 00`**                      | `ReflectionCubeMap`                 | **Кубическая текстура:** 6 граней DDS текстур (Right, Left, Top, Bottom, Front, Back).                                                                                   |
| **`98 00 41 00`**                      | `TgaTifTexture`                     | **Интерфейсные изображения:** Несжатые массивы BGRA пикселей (TGA / TIF).                                                                                                |
| **`00 00 A1 00`**                      | `TSESFXResource` / `SFXData`        | **Звуковые эффекты / Озвучка:** Сырые PCM RIFF/WAV аудиофайлы.                                                                                                           |
| **`35 00 41 00`**                      | `TREMeshResource`                   | **3D-Геометрия:** `VertexBuffer` (координаты, нормали, UV-координаты), `IndiceData` (индексы треугольников), `MeshBoneData` (скелетная привязка).                        |
| **`08 06 41 00`** .. **`36 06 41 00`** | `TREMaterialResource`               | **Материалы (Шейдерные слоты):** Связывают текстуры (Slot 30 = Diffuse, 42 = Normal Map, 43 = Cubemap, 44 = Mask) с параметрами шероховатости, отражений и прозрачности. |
| **`4B 00 41 00`**                      | `ObjectAsset` / `Entity`            | **Игровой объект:** Связывает скелет, меш, материалы и скриптовые якоря в сущность мира.                                                                                 |
| **`05 00 41 00`**                      | `TREAnimationResource`              | **Анимации:** Длительность (`uint32` в мкс), FPS (`float32`), треки костей (`7 0 65 0`).                                                                                 |
| **`1B 4C 75 61 50`** (`\x1bLuaP`)      | `TGCScript`                         | **Скрипты:** Байткод PUC-Rio **Lua 5.0.2** (декомпилируется через `unluac` или `luadec 5.0.2`). Заканчивается байтами `1B 80 00 00`.                                     |
| **Тег `0x1C`**                         | `XMLEntry`                          | **Квесты, диалоги, текст:** Чистый UTF-8 / ASCII XML текст (`System_Quests.xml`, `Tower_Buyable.xml`).                                                                   |

6. Почему старые инструменты сообщества не работали

1.  Отсутствие генерации футера 0xDEADBEEF: Инструменты Kull-Warrior и Rand-pass
    пересобирали тело, но оставляли старый или нулевой CRC32 в футере. Игра
    выбрасывала ошибку File Mismatch и закрывалась.
2.  Ошибка расчета data_size: Если при сборке в 12-й байт заголовка записать
    размер файла целиком (или размер с заголовком), игра падает с Assertion
    Failed (Visual C++ Runtime Error) из-за несовпадения размера буфера при
    чтении.
3.  Ложные контейнеры: При разборе сырых массивов пикселей байты ≥ 0x80
    принимались за таблицы оглавления, что раздувало файл на десятки килобайт
    лишних данных.

7. Архитектура для реализации редактора на Rust

Для написания быстрого и надежного редактора на Rust рекомендуется следующая
структура модулей:

src/
├── main.rs                   # CLI / GUI точка входа (например, eframe/egui или iced)
├── core/
│   ├── header.rs             # Чтение/запись заголовка 176 байт (Header)
│   ├── footer.rs             # Генерация 0xDEADBEEF, 0xFEEDDEAF и инвертированного CRC32 (crc32fast)
│   ├── node.rs               # Enum Node { Container(ContainerNode), Leaf(LeafNode) }
│   ├── parser.rs             # Рекурсивный парсер с жесткой валидацией границ
│   └── builder.rs            # Рекурсивная сборка байтов и таблиц смещений
└── assets/                   # Высокоуровневые конвертеры
    ├── dds.rs                # Сборка/разбор DXT1, DXT5, Mipmap цепочек
    ├── audio.rs              # Экспорт/импорт WAV PCM
    ├── xml.rs                # Работа с текстовыми таблицами
    └── lua.rs                # Интеграция с компилятором Lua 5.0

Рекомендуемые крейты (Rust Crates):

  - byteorder / binrw — быстрое чтение и запись Little-Endian структур.
  - crc32fast — расчет контрольной суммы на инструкциях процессора (SSE/AVX) с
    вызовом !hasher.finalize().
  - flate2 — компрессия/декомпрессия zlib (Deflate) для пожатых блоков.
  - serde / serde_json — сериализация манифеста проекта project.json.
  - image / ddsfile — декодирование и предпросмотр DDS-текстур.











Мы закрыли **95% ключевой логики** (именно поэтому круговой тест дал 100% совпадение байтов). 

Но если вы делаете профессиональный редактор на Rust, есть еще **несколько тонких нюансов и «подводных камней» движка**, о которых стоит знать заранее, чтобы ваш инструмент не споткнулся на сложных модах.

Вот 6 важных деталей, которые отлично дополнят техническую документацию:

---

### 1. Особенность карт (`.omp`) в сравнении с архивами (`.prp/.rpk`)

Архивы ресурсов (`.prp`, `.rpk`, `.psp`, `.pvp`) и карты локаций (`.omp`) используют один и тот же бинарный синтаксис чанков, но имеют **разное количество корневых таблиц**:
* **`.prp / .rpk`** содержит **одну** корневую таблицу (`ResourcePackRoot`), которая начинается со смещения `0xB0` (176 байт).
* **`.omp` (Карты)** содержит **ДВЕ** корневые таблицы подряд:
  1. `MapInfoEntry` — метаданные карты (настройки освещения, ссылки на используемые RPK).
  2. `MapRootEntry` — само тело карты (ландшафт, размещенные сущности, триггеры, спавны).
* **Ландшафт в `.omp` (`TerrainPoint`):** Каждая точка высоты ландшафта кодируется ровно в **4 байта**:
  * 12 бит — высота сетки (`Height = raw / 32.0`).
  * 4 бита — индекс основной текстуры земли.
  * 4 бита — маска травы/растительности (`Foliage`).
  * 4 бита — индекс текстуры скал/клиффов.
  * 4 бита — флаги проходимости.

---

### 2. Встроенный SDK лицевой анимации (FaceFX)

В дампах `CS PaladinBoss.prp` вы видели строки: `FACE`, `FxBone`, `FxCompiledFaceGraph`, `FxActor`, `Triumph Studios Overlord`.
* Это вшитые бинарные графы системы мимики **FaceFX SDK 1.x** (от *OC3 Entertainment*).
* Они привязаны к звуковым файлам (`.wav`) и автоматически управляют костями лица при разговоре персонажей.
* Если вы будете создавать полностью нового сюжетного NPC с кат-сценами, его блок лицевой анимации должен сохранять сигнатуру `FACE` (байты `46 41 43 45`).

---

### 3. Строгие ограничения виртуальной машины Lua

Движок игры компилирует и исполняет скрипты через **Lua 5.0.2** (а не современный Lua 5.1/5.4 или Luajit):
* Байткод всегда начинается с 4 байт: `\x1bLua` + байт версии `\x50` (ASCII `'P'`).
* **Размер типов данных в Lua VM:**
  * Размер `int` = 4 байта.
  * Размер `size_t` = 4 байта.
  * Размер инструкции = 4 байта.
  * Числовой тип `lua_Number` = 8 байт (стандартный IEEE-754 `double`).
* ⚠️ **Важно:** Если попытаться скормить игре байткод, скомпилированный компилятором `luac` от Lua 5.1+, игра мгновенно упадет при вызове `luaL_loadbuffer` из-за несовместимости формата опкодов.

---

### 4. Дескрипторы 3D-вершин (`VertexAttribute`)

Когда будете писать модуль импорта 3D-моделей (OBJ/FBX $\rightarrow$ PRP), геометрия в `VertexBufferInfo` описывается 32-битным флагом:
```rust
pub struct VertexAttribute {
    pub raw_descriptor: u32,
}

impl VertexAttribute {
    pub fn semantic(&self) -> u8 { ((self.raw_descriptor >> 16) & 0xFF) as u8 }
    pub fn format_flags(&self) -> u8 { ((self.raw_descriptor >> 24) & 0xFF) as u8 }
}
```
* **Семантики:** `0x01` — Позиция (XYZ), `0x04` — Нормаль, `0x05` — UV-развертка, `0x09` — Кватернион касательной (Tangent), `0x0A` — Веса костей (Skin Weights), `0x0B` — Индексы костей.
* **Размеры:** Флаг `1` = 8 байт (2x Float), `2` = 12 байт (3x Float / XYZ), `3` = 16 байт (4x Float), `4` = 1 байт, `15` = 4 байта (UByte4).

---

### 5. Структура поля `Hash2` в футере (байты `EOF - 4 .. EOF`)

В конце файла после CRC32 идут 4 байта:
* В `CS PaladinBoss.prp` это было число `268` (`0x010C`).
* В системных паках встречается константа `0x7C809B8B`.
* **Что это:** Это внутренний идентификатор ревизии сборки / счетчик зарегистрированных строковых ссылок.
* **Правило для редактора на Rust:** При распаковке всегда сохраняйте это 32-битное число в манифест `project.json` (как поле `footer_hash2`), а при пересборке просто записывайте его обратно в конец файла после расчетного CRC32.

---

### 6. Сжатие: Блочное vs Сплошное

* В 95% случаев архивы `.prp` **не пожаты целиком**, чтобы игра могла быстро считывать оглавление дерева, а внутри них пожаты **только отдельные тяжелые чанки** (пиксели текстур, файлы скриптов).
* Распознать сжатый блок в Rust тривиально: первые два байта `0x78 0x9C` (Default), `0x78 0xDA` (Max) или `0x78 0x01` (No compression / Low).

### Сводный чек-лист для начала кодинга на Rust:

1. [x] **Формат заголовка:** Ровно 176 байт Little-Endian (`Magic`, `v6.70`, `FileID`, `PayloadSize`, `Name[160]`).
2. [x] **Правило `data_size`:** $12$-й байт = чистый размер полезной нагрузки (Payload).
3. [x] **Парсер чанков:** Чтение `control_byte`, парсинг малых (2 байта) и больших (8 байт) оффсетов, отсечение ложных контейнеров.
4. [x] **Генератор оффсетов:** Рекурсивный расчет смещений при пересборке.
5. [x] **Контрольная сумма:** `!crc32fast::Hasher::finalize()` от всего файла до футера.
